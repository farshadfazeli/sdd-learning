SECTION 05 · PRACTICE

یک مثال کامل SDD؛ از ایده تا تست

در این مثال، دقیقاً می‌بینیم در هر بخش چه چیزی نوشته می‌شود، چرا لازم است و خروجی آن به مرحلهٔ بعد چه کمکی می‌کند.

سناریوی واقعی: لغو سفارش

فروشگاه آنلاین می‌خواهد مشتری بتواند سفارش را قبل از ارسال لغو کند. ما این قابلیت را با یک جریان کامل SDD طراحی می‌کنیم؛ از یک جملهٔ مبهم تا کد قابل‌آزمایش.

نقشهٔ مثال

01Requirementچه مسئله‌ای باید حل شود؟
02Clarificationچه ابهام‌هایی باید برطرف شود؟
03Specificationرفتار دقیق سیستم چیست؟
04Plan / Designچطور آن را بسازیم؟
05Tasksچه کارهای کوچکی لازم است؟
06Implementationکد و تست چطور نوشته می‌شود؟
07Verifyاز کجا بفهمیم درست است؟

بخش ۱: Requirement — نیازمندی

اینجا چه قرار می‌گیرد؟ هدف کسب‌وکار و نتیجه‌ای که کاربر می‌خواهد؛ بدون نام کلاس، دیتابیس یا راه‌حل فنی.

«به‌عنوان خریدار، می‌خواهم تا قبل از ارسال سفارش آن را لغو کنم تا اگر منصرف شدم، هزینهٔ ارسال ایجاد نشود.»

چرا؟ این جمله به تیم می‌گوید چه ارزشی باید ایجاد شود، اما هنوز جزئیات رفتاری را مشخص نکرده است.

بخش ۲: Clarification — رفع ابهام

اینجا چه قرار می‌گیرد؟ سؤال‌هایی که اگر پاسخشان مشخص نباشد، دو برنامه‌نویس ممکن است دو رفتار متفاوت بسازند.

چه کسی اجازه دارد؟

خود خریدار یا پشتیبانیِ دارای دسترسی؛ نه هر کاربر ناشناس.

در چه وضعیتی؟

Pending و Confirmed قابل لغو هستند؛ Shipped نیست.

بعد از لغو چه می‌شود؟

موجودی رزروشده آزاد و رویداد لغو منتشر می‌شود.

درخواست تکراری؟

نباید موجودی دوبار آزاد شود یا دو رویداد معتبر تولید شود.

بخش ۳: Specification — قرارداد رفتاری

اینجا چه قرار می‌گیرد؟ ورودی، قوانین، خروجی، خطاها و سناریوهای قابل‌بررسی. این بخش مرجع مشترک انسان، تیم و AI است.

Input / ورودیشناسهٔ سفارش و کاربر درخواست‌کننده
Rule / قانونسفارش ارسال‌شده قابل لغو نیست.
Success / موفقیتوضعیت به Cancelled تغییر کند.
Side effect / اثر جانبیموجودی آزاد و OrderCancelled منتشر شود.

Acceptance Criteria — معیار پذیرش

  1. اگر سفارش تأییدشده باشد، پاسخ موفق و وضعیت Cancelled برگردد.
  2. اگر سفارش ارسال شده باشد، خطای 409 برگردد و سفارش تغییر نکند.
  3. کاربر غیرمجاز پاسخ 403 بگیرد و هیچ اثر جانبی رخ ندهد.
  4. درخواست تکراری، آزادسازی یا رویداد تکراری ایجاد نکند.

بخش ۴: Plan / Design — طرح فنی

اینجا چه قرار می‌گیرد؟ تصمیم‌های فنی، محل تغییر فایل‌ها، مرز مسئولیت‌ها و ریسک‌ها؛ نه کد کامل.

APIPOST /orders/{id}/cancel — دریافت درخواست و برگرداندن نتیجه
Use caseCancelOrderHandler — بررسی کاربر و اجرای عملیات
DomainOrder.cancel() — کنترل transition مجاز وضعیت
EventOrderCancelled — انتشار فقط بعد از موفقیت تراکنش

بخش ۵: Tasks — کارهای اجرایی

اینجا چه قرار می‌گیرد؟ کارهای کوچک، مشخص و قابل انجام که هرکدام خروجی و معیار تکمیل دارند.

01

تغییر مدل سفارشافزودن Cancelled و متد cancel با بررسی transition.

02

ساخت Handlerبررسی مالکیت، وضعیت سفارش و خطاهای کاربردی.

03

افزودن APIساخت endpoint و نگاشت خطاها به HTTP status مناسب.

04

مدیریت اثر جانبیآزادسازی موجودی و انتشار event به‌صورت امن.

05

نوشتن تست‌هاپوشش موفقیت، خطا، دسترسی و idempotency.

بخش ۶: Implementation — پیاده‌سازی

اینجا چه قرار می‌گیرد؟ کد واقعی بر اساس طرح و Taskها. پیاده‌سازی نباید قانون جدیدی بسازد که در Specification وجود ندارد.

if (!order.CanBeCancelled())
    return Conflict("Order has already shipped");

order.Cancel();
await inventory.Release(order.Id);
await events.Publish(new OrderCancelled(order.Id));

این قطعه فقط نمونهٔ ساده است؛ در پروژهٔ واقعی باید تراکنش، تکرارپذیری، لاگ و مدیریت خطا هم با معماری پروژه هماهنگ شوند.

بخش ۷: Verify — اعتبارسنجی

اینجا چه قرار می‌گیرد؟ شواهدی که نشان می‌دهد خروجی واقعاً با Specification یکی است.

سناریونتیجهٔ مورد انتظارتست
لغو سفارش تأییدشده۲۰۰، Cancelled، یک eventUnit + Integration
لغو سفارش ارسال‌شده۴۰۹، بدون تغییرUnit
کاربر غیرمجاز۴۰۳، بدون آزادسازیIntegration
درخواست تکراریبدون اثر جانبی تکراریIdempotency
نتیجه: در SDD مسیر «نیازمندی ← Spec ← Design ← Tasks ← Code ← Test» قابل مشاهده است. اگر قانون لغو تغییر کند، دقیقاً می‌دانیم کدام بخش‌ها باید بازبینی شوند.
