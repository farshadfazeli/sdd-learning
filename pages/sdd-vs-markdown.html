Spec Kit یا OpenSpec؟

هر دو برای توسعهٔ مبتنی بر specification ساخته شده‌اند؛ اما یکی بیشتر روی فرایند استاندارد و ساختارمند تمرکز دارد و دیگری روی تغییرات کوچک و قابل مدیریت در پروژه‌های موجود.

خلاصهٔ یک‌خطی:

Spec Kit وقتی مناسب‌تر است که می‌خواهی از نیازمندی تا پیاده‌سازی یک مسیر رسمی و منظم داشته باشی. OpenSpec وقتی جذاب‌تر است که پروژه از قبل وجود دارد و می‌خواهی یک تغییر مشخص را با کمترین تشریفات، اما با specification قابل ردیابی انجام دهی.

GITHUB SPEC KIT

فرایندمحور و ساختارمند

برای تیمی که می‌خواهد قبل از کدنویسی، نیازمندی، طراحی، task و معیار پذیرش را با نظم مشخص تولید و بررسی کند.

OPENSPEC

تغییرمحور و سبک‌تر

برای تیمی که روی یک codebase موجود کار می‌کند و می‌خواهد هر تغییر را به‌صورت یک بستهٔ مستقل، قابل بررسی و قابل آرشیو مدیریت کند.

چرخهٔ هرکدام چگونه است؟

Spec Kit

  1. constitution: اصول پروژه
  2. specify: تعریف نیازمندی
  3. clarify: رفع ابهام
  4. plan: طراحی فنی
  5. tasks: خردکردن کار
  6. implement: ساخت و تست
  7. analyze / checklist: بازبینی

OpenSpec

  1. explore: شناخت مسئله و codebase
  2. propose: ساخت proposal و اسناد change
  3. apply: اجرای taskهای تغییر
  4. verify: بررسی انطباق با spec
  5. archive: ثبت تغییر تکمیل‌شده

چه زمانی کدام را انتخاب کنیم؟

Spec Kit را انتخاب کن اگر...

  • می‌خواهی تیم یک استاندارد و ترتیب مشخص داشته باشد.
  • feature پیچیده است و قبل از کدنویسی به طراحی دقیق نیاز دارد.
  • می‌خواهی اصول معماری و کیفیت از ابتدا enforce شوند.
  • تیم با workflow رسمی و artifactهای بیشتر مشکلی ندارد.

OpenSpec را انتخاب کن اگر...

  • پروژه از قبل ساخته شده و باید آن را مرحله‌به‌مرحله تغییر دهی.
  • قبل از تغییر، باید codebase فعلی را خوب explore کنی.
  • می‌خواهی هر change جداگانه، قابل verify و archive باشد.
  • فرایند سبک‌تر و قابل تنظیم‌تر برایت مهم است.
انتخاب عملی برای پروژهٔ ما:

اگر یک قابلیت بزرگ و جدید را از صفر طراحی می‌کنی، از Spec Kit شروع کن. اگر روی همین وب‌سایت یا یک repository موجود، تغییرهای مرحله‌ای انجام می‌دهی، OpenSpec می‌تواند انتخاب مناسب‌تری باشد. این دو رقیب مطلق نیستند؛ هر دو می‌توانند specification، طراحی، task و اعتبارسنجی را بهتر کنند، فقط نقطهٔ شروع و میزان رسمیت workflowشان فرق دارد.
